# Wazuh in Docker
[Español](06-wazuh-in-docker.md)

Procedure to deploy ENSFácil when Wazuh runs on the official Docker images
(`wazuh/wazuh-indexer`, `wazuh/wazuh-manager` and `wazuh/wazuh-dashboard`) with
the official `docker compose` deployment of `wazuh-docker`.

The plugin side (sections 3 to 12) is complete in this guide: dashboard image
with ENSFácil, start-up, role, configuration, seeding, validation, update,
rollback and removal. The manager side (section 13) describes the differences
from the [installation from scratch](01-installation-from-scratch.en.md) when
the manager runs in a container.

> [!note]
> `deploy-plugin.sh` and the commands with `systemctl`, `dpkg-query` and
> `/etc/wazuh-indexer/certs` in guides 01, 02, 04 and 07 apply to the package
> installation. In Docker, the procedures of this guide apply.

## 2. Prerequisites

### 2.1 The official Wazuh deployment

- Wazuh 4.14.7 deployed with the official `docker-compose.yml` of
  `wazuh-docker` (for example, the `single-node` folder), with the certificates
  generated by `generate-indexer-certs.yml` in `config/wazuh_indexer_ssl_certs/`
  (`admin.pem`, `admin-key.pem`, `root-ca.pem`, `wazuh.indexer.pem`, among
  others).
- Docker with the `compose` plugin, a user allowed to run `docker`, and
  access to Docker Hub to pull `debian:12`, `python:3.12-slim` and
  `node:22-alpine`.
- Authorised SSH access to the plugin repository in GitLab, to clone it
  (section 2.3).
- Internet access from the containers, so that `npx` can download `tsx` for
  the validation (section 9).
- `unzip` on the host, for the `--solo-id` check of the release (section 2.3).

From the compose folder, check that the three services are running version
4.14.7:

```bash
docker compose ps --format '{{.Service}} {{.Image}} {{.State}}'
docker network ls --filter name=_default
```

Expected result: `wazuh.indexer`, `wazuh.manager` and `wazuh.dashboard`, with
images tagged `4.14.7` and state `running`, and the compose network, named
`<compose folder>_default` (for example, `single-node_default`). If the version
differs, stop the procedure and refer to
[Version compatibility](03-version-compatibility.en.md).

> [!note]
> On macOS hosts, `generate-indexer-certs.yml` can leave
> `root-ca-manager.pem` and `root-ca-manager.key` uncopied, and the compose
> deployment does not start. The symptom and the fix are in
> [Troubleshooting, section 9.3](04-troubleshooting-and-rollback.en.md#93-known-problems-in-docker).

### 2.3 The release and the repository

Download and verify the ENSFácil release as in
[Installing from a release, sections 4 to 7](07-installing-from-a-release.en.md#4-prepare-the-folder-on-the-server).
Of its four files, Docker uses the zip, `create-admin-role.sh` and
`SHA256SUMS`; `deploy-plugin.sh` only for the `--solo-id` check of section 7
of guide 07, which needs `unzip` on the host.

Seeding and validation use the plugin repository (`config/` and the engine
that the validator imports). GitLab access is configured as in the
[installation from scratch, section 10.1](01-installation-from-scratch.en.md#101-validate-access-to-the-main-repository).

The working folders of this guide (`<repo>`, `<image>`, `<backups>`) are under
`/opt/ensfacil`, which section 4 of guide 07 creates as `root`. Assign it to
the user running the procedure and clone the repository:

```bash
sudo mkdir -p /opt/ensfacil
sudo chown "$USER":root /opt/ensfacil
git ls-remote git@gitlab.com:quersystem/plugin-wazuh-ens.git HEAD
git clone git@gitlab.com:quersystem/plugin-wazuh-ens.git <repo>
```

Expected result: a hash followed by `HEAD`, and the repository cloned in
`<repo>`.

### 2.4 Indexer query function

The indexer certificate of the official deployment is issued for the name
`wazuh.indexer`, which only resolves inside the compose network. From the
host, with `https://127.0.0.1:9200` and the deployment CA, curl rejects the
connection because the name does not match. For this reason the indexer
queries run from a container attached to that network, with no change on the
host.

The `ix` function sends a request to the indexer with the admin certificate
and verifies the indexer certificate against `root-ca.pem`. It takes the path
and, optionally, further curl options. Define it in the shell session, with
`<project>` and `<path>` replaced:

```bash
ix() {
  docker run --rm -i --network <project>_default \
    -v <path>/config/wazuh_indexer_ssl_certs:/certs:ro debian:12 bash -c '
      export DEBIAN_FRONTEND=noninteractive; apt-get -qq update </dev/null >/dev/null 2>&1 && apt-get -qq install -y curl </dev/null >/dev/null 2>&1 &&
      curl -s --cacert /certs/root-ca.pem --cert /certs/admin.pem --key /certs/admin-key.pem \
        "https://wazuh.indexer:9200/$1" "${@:2}"; echo' _ "$@"
}
```

The function is lost when the shell closes: define it again in a new session.
Each call installs `curl` in a new container and takes a few seconds.

## 3. Build the dashboard image with ENSFácil

ENSFácil is a plugin of its own (`ensfacil`), installed next to the Wazuh
plugin without modifying it. In Docker it is installed in a custom image based
on the official `wazuh/wazuh-dashboard:4.14.7`.

Prepare the build folder with the release zip, renamed to
`ensfacil-2.19.5.zip`:

```bash
mkdir -p <image>
cp <release>/ensfacil-1.1.0-osd-2.19.5.zip <image>/ensfacil-2.19.5.zip
```

Create `<image>/Dockerfile` with this content:

```dockerfile
FROM wazuh/wazuh-dashboard:4.14.7
ARG ENSFACIL_VERSION
COPY --chown=wazuh-dashboard:wazuh-dashboard ensfacil-2.19.5.zip /tmp/ensfacil-2.19.5.zip
RUN /usr/share/wazuh-dashboard/bin/opensearch-dashboards-plugin install file:///tmp/ensfacil-2.19.5.zip \
 && rm /tmp/ensfacil-2.19.5.zip
USER root
RUN python3 -c "import json,sys; f='/usr/share/wazuh-dashboard/package.json'; p=json.load(open(f)); v=[int(x) for x in sys.argv[1].split('.')]; p['build']['number']=str(int(p['build']['number'])+v[0]*10000+v[1]*100+v[2]); json.dump(p, open(f,'w'), indent=2); print('build.number', p['build']['number'])" "$ENSFACIL_VERSION"
USER wazuh-dashboard
```

The plugin is installed by the image's `wazuh-dashboard` user, without
`--allow-root` or `chown`. Only the `package.json` change runs as `root`.

Build the image, with the ENSFácil version of the zip in `ENSFACIL_VERSION` and
in the tag, and check it:

```bash
cd <image>
docker build --build-arg ENSFACIL_VERSION=1.1.0 -t wazuh-dashboard-ensfacil:1.1.0 .
docker run --rm --entrypoint /usr/share/wazuh-dashboard/bin/opensearch-dashboards-plugin \
  wazuh-dashboard-ensfacil:1.1.0 list
docker run --rm --entrypoint python3 wazuh-dashboard-ensfacil:1.1.0 \
  -c "import json; print(json.load(open('/usr/share/wazuh-dashboard/package.json'))['build']['number'])"
```

Expected result: the build finishes without errors; the plugin list includes
`ensfacil@1.1.0` next to `wazuh@4.14.7-01`; the `build.number` is `424801`.

The dashboard `build.number` forms the bundle URL of every plugin. The image
derives it from the ENSFácil version: the number of the official image
(`414701` in `wazuh/wazuh-dashboard:4.14.7`) plus X·10000 + Y·100 + Z for
version X.Y.Z. For 1.1.0 it is 414701 + 10000 + 100 + 0 = 424801. Each
ENSFácil version therefore has its own number and its own URLs, and browsers
download the new files when the version changes, including a return to an
earlier one. Without `--build-arg ENSFACIL_VERSION`, the build fails.

> [!important]
> The value of `ENSFACIL_VERSION` must be the version of the zip. With any
> other value, two images with different ENSFácil versions can share a
> `build.number`, and browsers would keep using the cached files.

## 4. Change the compose file and start

In `<path>/docker-compose.yml`, change the image of the `wazuh.dashboard`
service:

```yaml
  wazuh.dashboard:
    image: wazuh-dashboard-ensfacil:1.1.0
```

Recreate the service and check the start-up:

```bash
cd <path>
docker compose up -d
docker compose ps wazuh.dashboard
curl -sk -o /dev/null -w '%{http_code}\n' https://localhost/app/login
curl -sk -o /dev/null -w '%{http_code}\n' https://localhost/api/ensfacil/configuration
docker compose logs wazuh.dashboard | grep -o 'Setting up \[[0-9]*\] plugins: \[[^]]*\]' | tail -1
```

Expected result:

| Check | Expected result |
|---|---|
| `docker compose ps` | `wazuh.dashboard` with the image `wazuh-dashboard-ensfacil:1.1.0` and state `running` |
| `/app/login` | `200`, about 20 seconds after `docker compose up -d` |
| `/api/ensfacil/configuration` | `401`: the dashboard requires a session. Without a session, the response is `401` also without the plugin: this value is the expected one with the plugin installed, but it does not prove that the plugin loaded. The dashboard log and the same request with a session, which returns `200`, prove it |
| dashboard log | `Setting up [52] plugins: [...]`, with `ensfacil` in the list |

With a session open in the browser, `/api/ensfacil/configuration` returns
`200`. Before the first save, the response starts with
`{"configuration":null`.

If any check fails, stop the procedure and follow
[Troubleshooting, section 9](04-troubleshooting-and-rollback.en.md#9-docker).

## 5. Create the `ensfacil_admin` role

Saving the ENS configuration and viewing its history require the
`ensfacil_admin` or `all_access` role. The Wazuh `admin` user has
`all_access`: this step is only required if another user, without
`all_access`, must save the configuration or view its history. The role grants
no permission by itself; each user also needs their usual Wazuh role, with read
access to `wazuh-alerts-*` and `wazuh-monitoring-*`.

`create-admin-role.sh`, from the release folder, runs in a container attached
to the compose network, with the admin certificate of the deployment. First in
test mode, which sends no change:

```bash
docker run --rm --network <project>_default \
  -v <path>/config/wazuh_indexer_ssl_certs:/certs:ro \
  -v <release>/create-admin-role.sh:/t/create-admin-role.sh:ro \
  -e OS_CERT=/certs/admin.pem -e OS_KEY=/certs/admin-key.pem -e OS_CA=/certs/root-ca.pem \
  -e OS_URL=https://wazuh.indexer:9200 debian:12 \
  bash -c 'export DEBIAN_FRONTEND=noninteractive; apt-get -qq update >/dev/null 2>&1 && apt-get -qq install -y curl python3 >/dev/null 2>&1 && bash /t/create-admin-role.sh --dry-run --mapear <user>'
```

The following result corresponds to a role that is not yet assigned to any
user.

Expected result:

```text
== modo prueba: no se envía ningún cambio
== rol ensfacil_admin
PUT _plugins/_security/api/roles/ensfacil_admin {"description":"ENSFácil: puede cambiar la configuración ENS y ver su historial","cluster_permissions":[],"index_permissions":[],"tenant_permissions":[]}
== asignación de ensfacil_admin
PUT _plugins/_security/api/rolesmapping/ensfacil_admin {"users":["<user>"]}
```

If the role is already assigned to other users, the last request is a `PATCH`
that adds `<user>` without removing anyone.

Then the real run: the same command ending in
`bash /t/create-admin-role.sh --mapear <user>`, without `--dry-run`.

Expected result: `-> 201` (or `-> 200` if the role already existed) after each
request and, at the end, `usuarios con el rol ensfacil_admin: <user>`.

- The run can be repeated: the role is written the same way and only the
  missing users are added.
- Several users: `--mapear <user1> --mapear <user2>`.
- Without `--mapear`, the script only creates the role.
- If the user had a session open and still gets the 403 error, the user must
  log out and log in again.

> [!note]
> Alternative from the host: a `127.0.0.1 wazuh.indexer` entry in `/etc/hosts`
> allows `OS_URL=https://wazuh.indexer:9200` with port `9200` published by the
> compose deployment. This procedure uses the container because it requires no
> change on the host. In a multi-node cluster, the name is the one of the
> indexer node in its certificate
> (`openssl x509 -in <path>/config/wazuh_indexer_ssl_certs/wazuh.indexer.pem -noout -ext subjectAltName`).

## 6. First save of the configuration

In a new installation, the `active` document of the `wazuh-ens-configuration`
index does not exist until the first save. Until then, `inject-control.py`
stops with the message "no existe el documento 'active'…; guarda la
configuración una vez y vuelve a ejecutar" (the `active` document does not
exist; save the configuration once and run again).

Log in to Wazuh Dashboard with a user with `ensfacil_admin` or `all_access`,
open ENSFácil > Configuración and save the configuration once. Opening the
screen without saving does not create the document.

Check that the document exists:

```bash
ix 'wazuh-ens-configuration/_doc/active?filter_path=found,_source.documentType'
```

Expected result: `{"found":true,"_source":{"documentType":"ACTIVE_CONFIGURATION"}}`.

> [!warning]
> If the document does not exist, do not continue with the seeding until the
> first save is complete.

## 7. Back up the `active` document

Before each seeding or parameter change, save a copy of the document:

```bash
mkdir -p <backups>
COPY=<backups>/active-$(date +%Y%m%d-%H%M%S).json
ix wazuh-ens-configuration/_doc/active > "$COPY"
grep -c '"found":true' "$COPY"
```

Expected result: `1`. Restoring this copy in Docker is described in section
12.2.

## 8. Seed the controls

> [!important]
> Seed only once the ENSFácil image is deployed (section 4). The reason is in
> [Installing from a release, section 11](07-installing-from-a-release.en.md#11-update-to-a-newer-release).

`inject-control.py` runs in a `python:3.12-slim` container attached to the
compose network, with the `config/` folder of the repository mounted
read-only. For one control, without `--apply` it prints the plan and with
`--apply` it writes. The plan of one control:

```bash
docker run --rm --network <project>_default \
  -v <path>/config/wazuh_indexer_ssl_certs:/certs:ro -v <repo>/config:/cfg:ro \
  -e OS_CERT=/certs/admin.pem -e OS_KEY=/certs/admin-key.pem -e OS_CA=/certs/root-ca.pem \
  -e ENS_OS_URL=https://wazuh.indexer:9200 -w /cfg python:3.12-slim \
  python3 inject-control.py <control>
```

Expected result: the control's plan and, at the end, `== DRY-RUN ==`.

Seed the 23 controls. First the plan, without `--apply`, which writes nothing:

```bash
CONTROLS="mp.info.6 op.acc.1 op.acc.2 op.acc.3 op.acc.4 op.acc.5 op.acc.6 op.exp.1 op.exp.2 op.exp.3 op.exp.4 op.exp.5 op.exp.6 op.exp.7 op.exp.8 op.exp.9 op.exp.10 op.mon.1 op.mon.2 op.mon.3 op.nub.1 op.cont.2 op.cont.3"

for c in $CONTROLS; do
  echo "===== $c ====="
  docker run --rm --network <project>_default \
    -v <path>/config/wazuh_indexer_ssl_certs:/certs:ro -v <repo>/config:/cfg:ro \
    -e OS_CERT=/certs/admin.pem -e OS_KEY=/certs/admin-key.pem -e OS_CA=/certs/root-ca.pem \
    -e ENS_OS_URL=https://wazuh.indexer:9200 -w /cfg python:3.12-slim \
    python3 inject-control.py "$c" || break
done
```

Review the plan of each control: new parameters, values that are kept and, if
it appears, the line `YA NO EXISTEN en el bloque y se pierden` (no longer in
the block and lost). If the plan is correct, repeat the loop with
`python3 inject-control.py "$c" --apply`.

Expected result: `== APLICADO ==` for each control.

Seeding merges: it keeps the value of every parameter that already had one and
adds the missing ones. It also keeps the agents' settings (`configuration.agents`) and
the custom templates (`configuration.templates`).

With ENSFácil 1.3.0 or later, a control the document does not have can also be
added from ENSFácil > Configuración > Controles, with «Añadir con valores por
defecto» ([Configuration by controls and templates, section 5.1](09-configuration-by-system.en.md#51-add-a-catalog-control)).

> [!note]
> Evidence that depends on mandatory parameters without a value stays
> `NO_EVALUABLE`, with cause `CONFIGURATION`, and the requirements it supports
> are not accredited until those parameters are declared. Missing information
> is not interpreted as compliance.

## 9. Validate the document

A parameter with a value the plugin does not accept prevents the whole ENS
environment from loading, and the dashboard shows "No se pudo cargar el
entorno ENS" (the ENS environment could not be loaded). After each seeding or
parameter change, validate the whole document with the plugin validator
(`config/validate-configuration.ts`). The validator imports the plugin engine:
it needs the whole repository, not only `config/`.

```bash
ix wazuh-ens-configuration/_doc/active > <repo>/active.json
docker run --rm -v <repo>:/w -w /w node:22-alpine \
  sh -c 'npx --yes tsx config/validate-configuration.ts /w/active.json'
```

Expected result: `controles (23): mp.info.6 op.acc.1 …`,
`ESTRUCTURA VÁLIDA: el plugin cargará esta configuración.` and, with agent
settings, one line per agent; at the end, `AJUSTES DE AGENTES Y PLANTILLAS VÁLIDOS.`

A `scope` without the `agentIds` and `groupIds` arrays is rejected
(`configuration.scope.agentIds must be a string array`). The Configuración
screen always writes them; the error only appears in a document written by
hand.

> [!warning]
> If the validation fails, restore the copy from section 7 (section 12.2)
> before the dashboard is opened, and correct the reported parameter.

`<repo>/active.json` can be deleted after the validation.

## 10. Declare the policy: T and D levels

Parameter values are decisions of the person in charge and are declared in
ENSFácil > Configuración. The global configuration card also declares:

| Field | Controls | Not declared |
|---|---|---|
| ENS level | all | — |
| Nivel de Trazabilidad (T) (traceability level) | op.exp.8 | the ENS level applies |
| Nivel de Disponibilidad (D) (availability level) | op.cont.2 and op.cont.3, which only apply with D at ALTO | the ENS level applies |

With the ENS level at MEDIO and D not declared, op.cont.2 and op.cont.3 show
"No aplica" (not applicable).

To declare parameter values from a JSON file, `set-parameters.py` runs like
`inject-control.py`, with the file's folder mounted:

```bash
docker run --rm --network <project>_default \
  -v <path>/config/wazuh_indexer_ssl_certs:/certs:ro -v <repo>/config:/cfg:ro \
  -v <policy folder>:/pol:ro \
  -e OS_CERT=/certs/admin.pem -e OS_KEY=/certs/admin-key.pem \
  -e ENS_OS_URL=https://wazuh.indexer:9200 -w /cfg python:3.12-slim \
  python3 set-parameters.py /pol/policy.json
```

Without `--apply` it prints the plan; with `--apply` it writes.

Expected result: the changes per parameter and `DRY-RUN: nada escrito`; with
`--apply`, `<n> cambio(s) escritos en wazuh-ens-configuration/active`.

The file format and its rules are in the
[installation from scratch, section 14.5](01-installation-from-scratch.en.md#145-declare-the-policy).
For the `agents` section (an agent's template and own settings), mount the complete
repository, `-v <repo>:/repo:ro -w /repo/config`, instead of `<repo>/config`:
the tool reads the parameter classification from `public/`
([Configuration by controls and templates, section 11.1](09-configuration-by-system.en.md#111-declare-an-agents-template-and-settings-with-set-parameterspy)).
After declaring values, repeat the backup (section 7) before and the
validation (section 9) after.

## 11. Final check in the browser

Log in to Wazuh Dashboard and check that:

- in the menu, under "Security operations", "ENSFácil" appears;
- it opens on the Panel tab, with the tabs Panel, Configuración, Controles,
  Detalle del control, Informes, Evidencias and Eventos;
- the 23 controls appear;
- there is a "Máquina" selector to view all the machines in scope or a single
  one.

The controls measured on the manager (section 13) show data in the manager row
(agent `000`) after the first run of their collectors. Agents, groups and the
ENS scope are configured with the
[ENSFácil initial setup](https://gitlab.com/quersystem/ens-controls-runbook/initial-setup).

## 12. Update, roll back and remove

Each ENSFácil version is an image with its own tag. Installing, updating or
removing the image does not modify the indices: the ENS configuration, its
history and the runbook facts are kept.

### 12.1 Update to a new version

1. Read the notes of the new release: compatibility, new controls and new
   parameters.
2. Download and verify the release in its own folder
   ([Installing from a release, sections 4 to 7](07-installing-from-a-release.en.md#4-prepare-the-folder-on-the-server)).
3. Back up the `active` document (section 7).
4. Build the new image as in section 3, with the new version in the name of
   the source zip, in `ENSFACIL_VERSION` and in the tag. For example, for
   X.Y.Z:

   ```bash
   mkdir -p <new image>
   cp <image>/Dockerfile <new image>/
   cp <new release>/ensfacil-X.Y.Z-osd-2.19.5.zip <new image>/ensfacil-2.19.5.zip
   cd <new image>
   docker build --build-arg ENSFACIL_VERSION=X.Y.Z -t wazuh-dashboard-ensfacil:X.Y.Z .
   ```

   Expected result: that of section 3, with `ensfacil@X.Y.Z` and
   `build.number` = 414701 + X·10000 + Y·100 + Z.

5. Change the tag in `docker-compose.yml`
   (`image: wazuh-dashboard-ensfacil:X.Y.Z`), run `docker compose up -d` and
   check as in section 4. The plugin list of the new image must show
   `ensfacil@X.Y.Z`.
6. If the version brings new controls or parameters, seed them after the
   deployment (section 8) and validate the document (section 9).
7. Review the T and D levels (section 10).

Keep the previous image until the new one is validated: it is the rollback.

### 12.2 Go back to the previous version

Change the tag in `docker-compose.yml` to the previous version and recreate the
service:

```bash
docker image ls wazuh-dashboard-ensfacil
cd <path>
docker compose up -d
```

Expected result: the previous tag appears in the image list, and the checks of
section 4 give the same result with the previous version. If the previous
image no longer exists, build it again (section 3) from its release.

If the removed version seeded controls that the previous one does not know,
also restore the copy of the `active` document made before the update. The
`_source` of the copy is written back:

```bash
COPY=<backups>/active-YYYYMMDD-HHMMSS.json
docker run --rm -i python:3.12-slim \
  python3 -c "import json,sys; json.dump(json.load(sys.stdin)['_source'], sys.stdout, ensure_ascii=False)" \
  < "$COPY" > <backups>/active-restore.json
ix wazuh-ens-configuration/_doc/active -H 'Content-Type: application/json' -X PUT --data-binary @- \
  < <backups>/active-restore.json
```

Expected result: the response includes `"result":"updated"`. Then validate the
document (section 9) and reload the dashboard.

### 12.3 Remove ENSFácil

Go back to the official image in `docker-compose.yml`
(`image: wazuh/wazuh-dashboard:4.14.7`) and recreate the service:

```bash
cd <path>
docker compose up -d
```

Expected result: "ENSFácil" no longer appears in the dashboard menu.
Equivalent check from the host, with a session: after
`curl -sk -c cj -X POST https://localhost/auth/login -H 'osd-xsrf: true' -H 'Content-Type: application/json' -d '{"username":"<user>","password":"<password>"}'`,
`curl -sk -b cj -o /dev/null -w '%{http_code}\n' https://localhost/api/ensfacil/configuration`
returns `404` (with the plugin installed it returns `200`). Without a
session, the response is `401` in both cases and is not a valid check. The
`cj` file holds the session and is deleted afterwards.

The Wazuh plugin is the one of the official image and is not affected.

The ENS configuration stays in the `wazuh-ens-configuration` index and the
`ensfacil_admin` role in the security plugin. If ENSFácil will not be used
again in this environment, they can be deleted. This deletes the ENS
configuration and its history: before doing so, save a copy of the document
(section 7). Do not run this step if another installation uses the same
indexer.

```bash
ix _plugins/_security/api/rolesmapping/ensfacil_admin -X DELETE
ix _plugins/_security/api/roles/ensfacil_admin -X DELETE
ix wazuh-ens-configuration -X DELETE
docker image rm wazuh-dashboard-ensfacil:1.1.0
```

Expected result: `"status":"OK"` for the first two (for the first one,
`NOT_FOUND` if the role had no users), `"acknowledged":true` for the third,
and the image deleted. The facts stay in `wazuh-alerts-*` and expire with the
retention of those indices.

## 13. Manager side

The control rules and the manager collectors are installed with the
`install-manager.sh` of the runbooks, in the manager container. This section
describes the differences from the
[installation from scratch, sections 10 to 12](01-installation-from-scratch.en.md#10-configure-authorized-access-to-gitlab).
What is verified and what is pending is in section 1: inside the
`docker compose` deployment, this section is not verified.

### 13.1 What the manager image lacks

| Missing | Used by | Effect | Fix |
|---|---|---|---|
| `systemctl` | the `install-manager.sh` scripts, to restart the manager | the installer fails on restart and rolls back its change | `ENSFACIL_SYSTEMCTL` (section 13.5) |
| `flock` | the common emitter of every collector | no fact is written: the emitter exits with an error | package `util-linux-core` |
| `jq` | the `install-manager.sh` of op.exp.7, op.exp.8, op.exp.9, op.mon.1, op.mon.2, op.mon.3, op.nub.1 and op.cont.3, and the emitter | the installer stops. op.exp.7's tries to install `jq` with `apt-get` and the others ask for `apt-get install jq`; the image uses `dnf` | package `jq` |
| `hostname` | the emitter (`host` field of each fact) | `host` is empty | package `hostname`, or `ENS_HOST` (section 13.6) |
| `cron` | the manager collectors (op.exp.7, op.exp.8, op.exp.9, op.mon.1, op.mon.2, op.mon.3, op.nub.1 and op.cont.3) | they never run | host cron with `docker exec` (section 13.7) |
| `git` | cloning the runbooks | — | clone on the host and copy into the container (section 13.5) |

`python3` is present in the image. The `install-manager.sh` of op.mon.1 and
op.cont.3 use `sqlite3` or, if it is missing, the `sqlite3` module of
`python3`; without either, part of their evidence stays `NO_EVALUABLE`. Check
it (not verified in the image):

```bash
docker exec MGR python3 -c 'import sqlite3; print("SQLITE3=OK")'
```

Expected result: `SQLITE3=OK`.

### 13.2 Manager image with the tools

Whatever is installed with `dnf` inside a container is lost when it is
recreated. Pin the tools in a custom image, with the same version as the
official one:

```dockerfile
FROM wazuh/wazuh-manager:4.14.7
RUN dnf install -y jq util-linux-core hostname && dnf clean all
```

In `docker-compose.yml`, the `wazuh.manager` service then uses that image.

Temporary alternative without rebuilding the image. Changes are lost when the
container is recreated:

```bash
docker exec MGR dnf install -y jq util-linux-core hostname
docker exec MGR sh -c 'command -v jq flock hostname'
```

Expected result: the paths of `jq`, `flock` and `hostname`.

### 13.3 Persistence when the container is recreated

The official deployment mounts volumes on `/var/ossec/etc`, `/var/ossec/logs`,
`/var/ossec/queue`, `/var/ossec/api/configuration`,
`/var/ossec/var/multigroups`, `/var/ossec/integrations`,
`/var/ossec/active-response/bin`, `/var/ossec/agentless`, `/var/ossec/wodles`,
`/etc/filebeat` and `/var/lib/filebeat`.

| Path | Content | Persists |
|---|---|---|
| `/var/ossec/etc/rules/ensfacil_*.xml` | rules of the 22 controls with rules | yes, in the `/var/ossec/etc` volume |
| `/var/ossec/etc/shared/ens/agent.conf`, `…/ens-copias/agent.conf` | the agents' `<localfile>` entries | yes |
| `/var/ossec/etc/ossec.conf` | the manager's `<localfile>` entries (the eight manager collectors) | no, if `wazuh_manager.conf` is mounted (section 13.4) |
| `/etc/ensfacil/` | organization registers and `.env` | no: mount a volume |
| `/var/lib/ensfacil/` | collector state | no: mount a volume |
| `/var/log/ensfacil/` | fact files read by logcollector | no: mount a volume |
| `/opt/ensfacil-runbooks/` | copy of the runbooks (section 13.5) | no |
| `/opt/ensfacil/`, `/usr/local/bin/ens_op*` | libraries, templates and collectors | no |
| `/var/ossec/backup/` | backups made by the installers before each change | no (optional: mount a volume) |

```yaml
# docker-compose.yml, wazuh.manager service (add to its volumes)
      - ensfacil_etc:/etc/ensfacil
      - ensfacil_state:/var/lib/ensfacil
      - ensfacil_log:/var/log/ensfacil
# and declare ensfacil_etc, ensfacil_state and ensfacil_log in the volumes: section
```

After recreating the container, repeat the copy of the runbooks and the
`install-manager.sh` runs (section 13.5). The installers do not overwrite
`.env` or the organization registers.

### 13.4 The `<localfile>` entries in `wazuh_manager.conf`

The official deployment mounts `config/wazuh_cluster/wazuh_manager.conf` on
`/wazuh-config-mount/etc/ossec.conf`, and the image's start script copies it
over `/var/ossec/etc/ossec.conf` on every start. The `<localfile>` entries that
the `install-manager.sh` scripts add to `ossec.conf` disappear at the next
container start, and those controls are left without data.

Before running the installers, append this block to
`<path>/config/wazuh_cluster/wazuh_manager.conf`, on the host:

```xml
<!-- ENSFácil: hechos de los recolectores del manager -->
<ossec_config>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_exp_7.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_exp_8.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_exp_9.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_mon_1.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_mon_2.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_mon_3.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_nub_1.json</location>
  </localfile>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/ensfacil/op_cont_3.json</location>
  </localfile>
</ossec_config>
```

Apply the file by restarting the manager container:

```bash
cd <path>
docker compose restart wazuh.manager
docker exec MGR grep -c 'ENSFácil: hechos de los recolectores del manager' /var/ossec/etc/ossec.conf
```

Expected result: `1`.

Each `install-manager.sh` checks whether its `<location>` is already in
`ossec.conf` and, if so, does not add it again (message "el localfile de … ya
está en …"). With the block already applied, the installers do not duplicate
the reading of any file.

From this point on, restart the manager with
`docker exec MGR /var/ossec/bin/wazuh-control restart`. A container restart
(`docker restart` or `docker compose restart`) copies `wazuh_manager.conf`
again and discards any change to `ossec.conf` that is not in that file.

### 13.5 Groups, prior backup and installers without systemd

Clone the runbooks on the host, in `/opt/ensfacil`, with the
`/opt/ensfacil/runbooks.txt` file, as in the
[installation from scratch, sections 10.3 and 10.4](01-installation-from-scratch.en.md#103-clone-the-ens-runbooks).

Create the `ens` and `ens-copias` groups and check their `agent.conf`:

```bash
docker exec MGR /var/ossec/bin/agent_groups -a -g ens -q
docker exec MGR /var/ossec/bin/agent_groups -a -g ens-copias -q
docker exec MGR grep -c '<agent_config' /var/ossec/etc/shared/ens/agent.conf
docker exec MGR grep -c '<agent_config' /var/ossec/etc/shared/ens-copias/agent.conf
```

Expected result: `1` for both checks. The `install-manager.sh` scripts refuse
to modify an `agent.conf` with no `<agent_config>` block or with more than one
([installation from scratch, section 11](01-installation-from-scratch.en.md#11-create-and-validate-the-ens-group)).

Save a copy of the manager configuration on the host:

```bash
mkdir -p <backups>
docker exec MGR tar czf - -C /var/ossec etc/rules etc/decoders etc/shared/ens etc/shared/ens-copias etc/ossec.conf \
  > <backups>/manager-$(date +%Y%m%d-%H%M%S).tar.gz
```

Expected result: the `.tar.gz` file in `<backups>`, with no error messages.

Copy into the container only the runbook folders listed in `runbooks.txt`:

```bash
docker exec MGR mkdir -p /opt/ensfacil-runbooks
while read -r r; do
  docker cp "/opt/ensfacil/$r/." "MGR:/opt/ensfacil-runbooks/$r" || { echo "ERROR: $r"; break; }
done < /opt/ensfacil/runbooks.txt
```

Expected result: no `ERROR` line.

The `install-manager.sh` scripts read `SYSTEMCTL="${ENSFACIL_SYSTEMCTL:-systemctl}"`
and only use it for `"$SYSTEMCTL" restart wazuh-manager`, also in their
rollback. `wazuh-control restart wazuh-manager` ignores the second argument,
restarts every daemon and returns an error if the configuration is invalid or a
daemon does not start, so the installers' rollback keeps working. The scripts
are not modified: the variable is enough.

```bash
while read -r r; do
  echo "===== $r ====="
  docker exec -e ENSFACIL_SYSTEMCTL=/var/ossec/bin/wazuh-control MGR \
    bash "/opt/ensfacil-runbooks/$r/install-manager.sh" || { echo "ERROR: $r"; break; }
done < /opt/ensfacil/runbooks.txt
```

Expected result: no `ERROR` line. Each installer ends with its `wazuh-logtest`
check.

### 13.6 The host name without the `hostname` command

The common emitter (`/opt/ensfacil/ensfacil-emit.sh`) takes the `host` field
from `ENS_HOST` and, if it is not set, from `$(hostname)`. There are two
options:

- with the image of section 13.2 (`hostname` installed), the value is the
  container name. Setting it with `hostname:` in `docker-compose.yml` (the
  official one uses `wazuh.manager`) is recommended so that it does not change
  when the container is recreated;
- pass `-e ENS_HOST=<name>` on every `docker exec` (section 13.7).

The manager collectors make no other call to `hostname`. The only exception:
op.exp.9 recognizes the manager itself in the `sistemas` column of the
incident register by the container name (Python's `socket.gethostname()`). A
fixed `hostname:` keeps that value stable.

### 13.7 Schedule the collectors from the host

(not verified in a container).

## 14. Known limitations in a container

- **op.mon.3 agent collector.** Besides the manager collector, the op.mon.3
  `install.sh` installs `ens_opmon3_agent_collect.sh` with an hourly cron on
  each machine in the `ens` group. It runs on the audited machine, not in the
  manager container.
- **op.exp.8 EV-13** (logging system services). The collector asks systemd for
  the state of `wazuh-manager`, `wazuh-indexer` and `wazuh-dashboard`. The
  container has no systemd: it emits `activo=desconocido`, which the dashboard
  judges `NO_CUMPLE`. No variable avoids it; adapting the collector is
  pending. Do not simulate `systemctl`: it would produce false evidence.
- **op.exp.8 in the manager row.** It also measures the server itself (auditd,
  journald, time). The container has no auditd and the result is "no
  instalado" (not installed). What should be measured on the host running
  Docker is not verified.
- **Multi-node cluster.** Not verified. Rules and `agent.conf` files are
  synchronized from the master; the manager collectors and their `<localfile>`
  entries would go on the master.
